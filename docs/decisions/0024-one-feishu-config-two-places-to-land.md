# ADR-0024 · 飞书只填一次；凭据落两处，看门狗那份不许依赖 agent

- **日期**：2026-08-23
- **状态**：已采纳
- **相关**：IvyeaAgent 的 ADR-0017（店铺巡检与审批闭环）、ADR-0018（多店铺巡检）

## 背景

飞书在这套系统里同时喂五条链路：

| 链路 | 谁在跑 | 以前读哪份配置 |
|---|---|---|
| 服务器 CPU 告警 | `scripts/cpu_alert.py`（cron，独立进程） | `hub_settings.json` 的 `alert_*` |
| 事件通知（任务失败/超预算） | IvyeaOps 后端 | `notify_webhook` → `alert_webhook` |
| 店铺巡检卡片 | IvyeaAgent | `~/.ivyea/.env` + `settings.json` |
| 审批按钮回调 | feishu-ivyea-relay | `/etc/feishu-ivyea-relay.env` |
| 飞书里和 AI 对话 | feishu-ivyea-relay | 同上 |

同一个飞书应用要在**三个地方各填一遍**，而且这三处互不知情。本机实测（2026-08-23）：
agent 与 relay 用的是同一个应用，IvyeaOps 那份 `alert_*` 全空、实际靠一条
「回退到 `/root/.hermes/.env`」的兼容分支在跑——那个分支对开源用户是死路，
他们机器上没有 Hermes。

漏配任何一处的表现完全一样：**保存成功、界面一切正常、就是收不到消息**，没有报错。

## 决策

### 一、界面只有一个入口，凭据落两处

IvyeaOps 系统配置页是唯一填写入口。保存时：

- 写 `hub_settings.json`（`alert_*` 那一组，键名不变，存量安装零改动）；
- 同时 `POST` 给 IvyeaAgent 的 `/v1/config/feishu`，由它写 `~/.ivyea`。

### 二、看门狗那份**故意**不合并

CPU 告警是**看门狗**：它要报的恰恰是「这台机器/这个进程不正常了」。让它去读
IvyeaAgent 的配置、或经由 8765 取凭据，等于在最需要报警的时候没有报警。
所以它继续读自己那份 `hub_settings.json`，跑在独立进程里，不依赖 agent 存活。

「两处各存一份」在别处通常是坏味道，这里是有意的**故障隔离**——代价（保存时多推一次）
远小于收益（agent 挂了照样能收到告警）。真正要消灭的是**两处各填一遍**，那个已经没了。

### 三、白名单和巡检任务只存 IvyeaAgent 一份

它们没有"agent 挂了还要用"的场景，不需要冗余。ops 侧不留副本，界面直接读写 agent 的
端点。存两份必然长期不一致，而白名单不一致意味着**撤权失败**。

### 四、relay 改成 agent 配置优先、env 兜底

与"环境变量覆盖配置文件"的常规习惯相反。理由在撤权：env 优先的话，在界面上把某人
从审批白名单里删掉——界面上没了、保存也成功——relay 还认着 env 里的旧名单继续放行。
配错顶多是发不出消息，撤权失败是真会花钱的。所以让**能在界面上改的那一份**说了算，
env 只在界面从没配过（键不存在）时生效。

判定改成每次现取，不再用启动快照：白名单改完必须立刻生效，不能要求重启 relay。

## 理由

**为什么不给飞书凭据起一组新键（`feishu_*`）而是沿用 `alert_*`**：新键要么让存量安装
重填一遍，要么写一套"新键为空就回退老键"的解析——那正是这次要消灭的东西。
键名难看是一次性的，迁移成本是每个用户的。

**为什么能力要按条列而不是一个"飞书已连接"的绿灯**：五条链路的门槛不一样。
群机器人 Webhook 能发文本告警，但它**没有回调通道**，永远点不了审批按钮。
一个总绿灯会让只配了 Webhook 的人以为一切就绪，然后困惑于卡片上为什么没有按钮。

**为什么向导的 ✓ 必须来自可核实状态**：配置类界面最常见的谎是"你点过下一步就算完成"。
这里每一步的完成判据都是能查的事实——凭据在不在、`systemctl is-active` 说 relay 跑没跑、
巡检任务注册了几条、测试消息**真的发出去过**。查不到的时候报 unknown，不报失败：
Windows 上没有 systemd，把 relay 显示成"已停止"会让人去修一个不存在的服务。

## 实测记录（同日，真实应用）

- `im/v1/chats` 返回 `code=0` + **空 items**，尽管机器人确实在群里、卡片也发得进去。
  它只列"应用可管理"的群。因此界面必须同时支持手工粘 `oc_` 开头的 chat_id，
  不能把"选群"做成唯一入口。
- `im/v1/chats/{id}/members` 正常返回成员的 `open_id` 与姓名 —— 审批人可以勾选，
  这是这次唯一真正能"可视化"掉的手抄环节。

## 影响

- 存量安装：`alert_*` 键名与环境变量不变，CPU 告警行为不变。新增
  `alert_feishu_domain`（默认 `feishu`），国际用户可切 `lark`。
- 老版本 IvyeaAgent（没有 `/v1/config/feishu`）：下推失败只记日志，保存照常成功，
  CPU 告警不受影响。
- relay 的启动硬门槛从"凭据 + 白名单"收窄为"凭据"。白名单为空改为启动警告——
  把关仍在 `gates.sender_allowed`（空名单拒绝所有人），去掉的只是
  "填完凭据想先起来试试对话，却因为还没指定审批人而起不来"这个配置期死结。
