# ADR-0035 · 产物卡片挂在回答下面；命令写出来的文件也要记

- **日期**：2026-09-10
- **状态**：已采纳
- **依据**：2026-09-10 会话；前身是 [ADR-0033](./0033-console-artifacts-are-addressed-by-id.md)

## 背景

任务台的产物下载/预览（v1.13.9）上线后，维护者实测的反馈是"我刚才测试了一下压根
没看到"。查生产库，`console_files` 表**从上线到当时是 0 行** —— 功能是完整的，但
没有任何真实产出走到它。

两处断点：

1. **记不上**。`file_change` 事件只有 `write_file` / `edit_file` 两个工具会发。而翻
   最近的会话存档，实际用的是 `run_python`（20 次）、`run_command`、`mcp_call_tool`
   —— 报表和图表都是跑脚本写出来的，这条路一条都不记。
2. **找不到**。就算记上了，出口是右侧一条 40px 的图标条，而且那一格**没数据时根本
   不显示**。一个要先知道它在哪才找得到的出口，等于没有出口。

## 决策

1. Agent 侧：`_run`（run_command / run_python 共用）在子进程跑完后扫一遍工作区，
   把 mtime 晚于命令开始时间的文件记成文件变更。
2. Ops 侧：产物卡片铺进消息流，挂在**产出它的那条回答**下面；点开是右侧抽屉预览，
   卡片上直接带下载。右侧产物栏保留作汇总视角。

## 理由

**为什么扫 mtime 而不是要求模型用 write_file。** 让模型改习惯是最不可靠的一种修法
——它想用 shell 就会用 shell，而且脚本产出的文件本来就是最典型的"任务产物"。扫描
的代价可控：跳过 `.git` / `node_modules` / `dist` 等噪音目录，限深 5 层、限扫 4000
个文件、条数受既有的 40 条上限约束，扫描抛异常一律吞掉（产物索引是附加值，不能
影响命令本身的结果）。

**为什么 action 记 `write` 而不是 create/overwrite。** 拿不到改之前的内容，就不知道
是新建还是覆盖。不知道就别猜 —— UI 上照实说"写出"。

**为什么归轮按时间而不是按 turn_id。** 库里确实记了 `turn_id`（这次一并加的），但
页面上的轮次 id 是前端自己生成的，恢复历史会话时更是重新缝出来的，两边对不上。而
每一轮的结束时刻是现成的：一个文件属于**第一个"结束时刻不早于它"的回答**。正在跑
的那一轮没有结束时刻，于是刚写出来的文件自然落到它下面 —— 这正是最常见的一幕：
跑完当场就想把东西拿走。

**为什么预览改成右侧抽屉。** 看的是一份文档，左边的对话得留着；一边对照原文一边看
结论是这个面板最常见的用法，居中弹窗会把对话整个盖掉。

## 后果

- **"功能写完了但入口没接"这件事，这个仓库里已经反复出现。**判据要立起来：一个新
  出口上线后，先去数据层查一眼它到底有没有被走到（这次就是 `select count(*)` 一句话
  的事），而不是等用户来说"没看到"。
- 命令产物的记录依赖工作区。写到工作区之外（`/tmp` 等）的文件仍然不会被记上 ——
  这是有意的边界，扫全盘不可接受。
- 扫描只在**前台**命令后跑；`run_in_background` 起的进程写的文件不在射程内，
  它们的产出时刻不确定，等它结束再扫需要另一套机制。
