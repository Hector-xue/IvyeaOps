# ADR-0029：领星 ERP 并入运营驾驶舱

- 日期：2026-08-29
- 状态：已采纳

## 背景

「运营驾驶舱」和「领星 ERP」一直是两个并列的板块。看上去分工清楚——一个看市场，
一个连 ERP——但它们其实是同一件事被切成了两半，而切口正好落在用户干活的中间。

四处硬重叠，都不是观感问题：

1. **同一个工单系统，两层壳。** `/api/cockpit/ads/adjust` 和
   `/api/lingxing/operate/manual` 调的是同一个 `lingxing_operate.create_manual_ticket`、
   同一份存储、同一套护栏与复核。于是：**在广告看板点「调预算」生成的工单，必须切到
   另一个板块才能确认**，而两个板块之间连一个跳转都没有。
2. **两个广告面板同源同口径。** `ads_board_service` 与 `lingxing_dashboard` 从同一批
   SP 日报表聚合，本期窗口都是 `1..days`（都不含今天）、`prev` 都是 `days+1..2*days`。
   前者是后者的**严格超集**：多出目标 ACOS、今日预算进度、异常标注 + 可执行意图、
   小时曲线、跳过没开通广告的店。
3. **同一套凭证与总开关**（`lingxing_enabled` + OpenAPI 凭证），但配置入口只在领星
   板块里。驾驶舱那两块没配好时只能甩一行 400 文本，没有去处。
4. **顶栏两套选择器语义打架。** 驾驶舱按**站点**（marketplace）取数，领星按**店铺**
   （sid）取数。并排放着，没人分得清哪个管哪边。

## 决策

**领星 ERP 整体并入运营驾驶舱**，`/lingxing` 保留为重定向。

反过来做（驾驶舱并进领星）会把 5 个全员可见的市场标签拖进一个 admin-only 板块，
不可接受。

### 结构

```
市场（全员）      大盘流量 · 关键词 · 竞品监控 · 自有ASIN · 类目大盘
自家店铺（admin） 促销日历 · 广告看板 · 优化建议 · 工单⑤
⚙ 领星工具        数据浏览 · 审计 · 配置          （AppDialog）
```

- **顶栏那一条随组切换**：市场组给数据源+站点，经营组给连接状态芯片+店铺选择器。
- **三个低频工具入口收进对话框**，复用 `components/AppDialog`（`SettingsDialog`
  已是先例）。它们不该和「广告看板」抢同一行。
- **不做双入口灰度。** 撤掉侧栏「系统配置」那次已经确立过原则：同一件事两个入口，
  迟早各自演化。

### 撤掉领星「大盘」，由广告看板承接

大盘独有的两样东西补进广告看板，一样都不丢：本币金额、分店对比表。币种取
`/api/cockpit/ads` 返回的确切 `currency`，不再像大盘那样从店名去猜。

顺带修掉一个一直存在的读数陷阱：**跨币种时顶部合计是不同币种直接相加**。现在只有
全场同币才标货币符号，否则明写"只能看涨跌趋势，不能当金额读"并指向分店表。

## 明确不做

- **不合并 `/api/cockpit` 与 `/api/lingxing` 两个路由前缀。** 会动
  `test_cockpit_routes.py` 的契约断言和整个 `api/cockpit.ts`，换不来任何用户可见的
  好处。
- **不删 `lingxing_dashboard`。** UI 已经不用它了，但 `ivyea_ops_tools` 的
  `lingxing_dashboard` 工具直接 import 路由函数 —— 改成 `ads_board` 的瘦封装等于
  悄悄换掉一个 agent 工具的输出 schema。那是另一侧的契约，不该被一次前端重构顺手
  改掉。原样保留，加注释写清它现在服务谁。
- 不动 RBAC 模型（领星仍是 admin-only，`MODULE_CATALOG` 不变）。
- 不动写通道的任何一道闸。

## 四件被真实踩到的工程约束

写下来是因为它们都**不会报错**，只会静悄悄地坏掉：

1. **经营侧必须 lazy。** `Home` 是 eager（属 shell，和 Login/Setup 一起进首屏包）。
   按朴素写法直接 import，领星那三千多行会进首屏，连永远看不到这些标签的非管理员
   也要下载。现在拆成 7 个独立 chunk（约 74 kB），eager 包 372.19 → 365.98 kB。
2. **非管理员会白屏。** 标签初始值从 localStorage 读，降权用户正好存着 `ads` 时，
   `OpsContextBar` 会在没有 provider 的情况下 `useLingXing()`，整个板块被
   ErrorBoundary 接走。初始值要过权限，`isOps` 还要再叠一道 `isAdmin`。
3. **`alive` ref 在 StrictMode 下会永久为 false。** 只在 cleanup 里置 false 的写法，
   经过 mount→unmount→mount 之后每个 `setState` 都被跳过 —— 面板停在"正在加载…"，
   一行报错都没有。进来时必须显式设回 true。
4. **`.home-tab` 的 `flex-shrink:0` + `nowrap` 桌面端也要有。** 这两条以前只写在
   760px 的媒体查询里（那时只有 7 个标签）；9 个标签在 1440px 桌面端就把"大盘流量"
   压成了竖排两行。

## 轮询

合并前三个组件各轮各的（`LingXing` 10s / `LingXingOperate` 5s / `LingXingAudit` 8s）。
那时它们是互斥的标签，同一刻只有一个活着，所以从没撞上。合并后工单徽标要常驻、
对话框可能和标签同时开着，再各轮就是几份请求叠着打领星的限流接口（约 340ms/次），
挤掉真正要用配额的读操作。

status / sellers / datasets 收进 `LingXingProvider` **只跑一份**；工单列表仍由工单页
自己轮——那是它自己的数据。**provider 只包管理员**：非管理员不该被代替着去打管理员
专属接口。

## 代价

- 标签行有 9 个标签 + 2 个分组标签。侧栏收起时 1440px 放得下；展开时需要横向滚动
  （移动端本来就滚，页面本身不会横向溢出）。这是 9 个标签的自然结果，用滚动兜住。
- `lingxingUi` 与 `home/*` 两套 UI 原语暂时并存（`Btn/LxTable` vs `.cp-btn/.cp-table`）。
  统一它们要动 5 个组件上千行，会把一次结构改动膨胀成大范围视觉改动，留待后续。
