# ADR-0021 · 任务台切模型只影响当前会话，改全局是另一条明路

- **日期**：2026-08-21
- **状态**：已采纳
- **依据**：本次「输入框那枚模型芯片能不能直接切主脑」的需求

## 背景

任务台输入框右下角一直有一枚显示当前主脑模型的芯片，但它点了只会跳「系统配置」。
代码里那段注释写得很清楚，当时的判断也没错：

> 只显示，不在这里切：agent 的模型是全局配置（`/v1/model/configure`），不支持按轮次
> 覆盖；做成下拉框会是个点了没反应的假开关。

于是想换个模型试试，就得离开对话去翻系统配置、在自由文本框里手打模型名。而
IvyeaAgent 的 CLI 里 `/model` 一条命令就换了 —— 同一个产品两套操作方式。

三个独立的槽位（主脑 / 视觉复核 / 生图）各要填 Provider + 模型名 + 密钥 + 地址四样，
模型名还是纯手输，得自己背 `Qwen/Qwen3-VL-30B-A3B-Instruct` 这种字符串。

## 决策

1. **IvyeaAgent 支持按轮次指定模型**（v1.15.4，`chat` / `chat/stream` 的 `model` 字段）。
2. 任务台那枚芯片变成真的选择器，选中的模型**逐轮下发，只影响当前浏览器的这条会话**；
   `/model` 命令做同一件事。
3. 想改全局是面板底部**另一个**按钮「设为默认」，带二次确认，写的是 ops 的系统配置。
4. 各槽位的模型名从自由文本换成"可搜索清单 + 仍可手输"，并给「沿用主脑账号」这类
   一键继承。

## 理由

**为什么不让芯片直接改全局**：agent 的主脑是一个进程级的全局设置。IvyeaOps 是多用户
的，还有一堆定时任务在跑 —— 一个人在输入框里随手试个模型，不该把别人的对话和后台任务
一起换掉。按轮次下发天然是"谁选谁生效"。

**为什么老版本 agent 不给下拉框**：老 agent 会直接忽略 `model` 字段。那种情况下给个
选择器，用户选了 A、跑的还是 B，且没有任何提示 —— 比不给更糟。所以前端按
`health.version` 门控，低于 v1.15.4 就退回原来的"跳系统配置"。

**为什么覆盖失败要报错而不是回落主脑**：同上，静默回落就是假开关。选了没配密钥的模型，
当场告诉他缺哪个环境变量，比让他拿着"怎么答得跟以前一样"去猜强。

**为什么模型清单要新开一个端点**：已有的 `/v1/model/providers/{id}/models` 只认 agent
内置 provider 表里那 23 家，密钥也只从 agent 自己的 `.env` 取。而 ops 的视觉槽/生图槽
常指向内置表里根本没有的中转商（apimart、硅基流动），密钥又存在 ops 那边 —— 两个条件
都不满足。新的 `POST /v1/model/catalog` 接受调用方现给的 `base_url` + `api_key`。

**为什么保留手输**：实测 apimart 的 `/models` 返回 402（余额不足），硅基流动能返回 94 个。
中转商的清单接口靠不住是常态，拉不到时输入框是唯一出路，下拉只能是加法。

## 后果

- 前后端多了一处**版本耦合**：`modelSwitchable` 钉在 agent ≥ v1.15.4。以后再加这类字段
  要记得同样门控，不能默认新版。
- 「设为默认」换 Provider 时会**清空 ops 存的那把 `ivyea_agent_api_key`**。不清的话
  `sync_model_settings` 会把旧 Provider 的 key 写进新 Provider 的环境变量，把人家原本
  配好的 key 覆盖掉，而且毫无征兆。清空只是"不再下推"，agent `.env` 里各家已有的 key
  一个都不动。
- 服务端会去访问调用方现给的地址，所以 `/v1/model/catalog` 只放行 `http(s)://` ——
  urllib 认 `file://`，不挡就是一个任意读本机文件的口子。
- ops 前端那份硬编码的 `PROVIDERS`（12 家）和 agent 的内置表（23 家）**仍然是两套**，
  已经对不上（siliconflow/dashscope 只 ops 有，doubao/minimax/xai 只 agent 有）。这次
  没动它：ops 服务端的 `ASSISTANT_PROVIDER_BASE` 认的是 ops 那套 id，改 id 会连带碰坏
  ops 自己的文本链。收口另立条目做。
