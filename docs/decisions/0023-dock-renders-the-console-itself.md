# ADR-0023 · 悬浮球不再自己实现对话，直接渲染任务台

- **日期**：2026-08-21
- **状态**：已采纳
- **依据**：用户反馈「右下角的浮标对话窗口和任务台的差距太大了，连审批确认的功能都没有」

## 背景

右下角悬浮球和任务台是**两份**对话实现。悬浮球那份只有：流式正文、一行工具叙述、
历史列表。任务台那份有：审批三档、写操作确认卡、执行步骤流、待办、上下文进度条、
统计条、模型切换、附图、@ 引用、`/` 命令、预设、技能、工作区、断链恢复。

而且悬浮球把 `plan_mode` 写死成 `true` —— 也就是**永远只读**，用户在那里让 Agent 干
写操作，它只会给方案，不会（也不能）落地。

两份各自演化的必然结果就是差距越拉越大。逐个补功能只是把这个结构继续维持下去。

## 决策

悬浮球降级为**外壳**：悬浮球本体（可拖、记位置）、面板头（新会话 / 历史 / 刷新 / 收起）、
历史会话列表。对话区直接渲染 `<Console embedded />`。

`Console` 新增 `embedded` 模式，只关掉三件与"页面"绑定的事：
读写地址栏、右侧产物栏、大 Hero。其余全部照旧。

## 理由

**为什么不是"把缺的功能补进悬浮球"**：那要把审批状态机、步骤缝合、断链恢复、
上下文快照再写一遍。这些恰恰是这套系统里最容易出错、也真的出过事故的部分
（见 ADR-0011）。写第二遍就是把事故面积翻倍。

**为什么不是"把任务台的逻辑抽成 hook 给两边用"**：那样两边的**渲染**仍然是两份，
差距会从"能力"转移到"呈现"——步骤流长什么样、确认卡摆在哪、进度条显不显示，
还是会各走各的。直接渲染同一个组件，才是构造上的一致。

**代价**：任务台那一份比悬浮球重（启动要拉技能、预设、能力目录）。所以做成
"打开过一次才挂载，之后一直挂着（收起只用 CSS 藏）"：没人用的时候不付这份钱，
用过之后收起面板也不会把正在跑的那一轮连同上下文一起丢掉 —— 而"问一句、收起来
接着干活、回头看结果"正是悬浮球最典型的用法。

## 后果

- 悬浮球从 899 行降到约 330 行，并删掉了一批早已不渲染的知识库遗留代码。
- **新会话不能走全局事件**。侧边栏「新建任务」广播的 `CONSOLE_NEW_EVENT` 说的是
  "页面那一份开一轮新的"；两份都听，就会出现"在悬浮球里点新会话、页面上正跑着的
  那轮被清掉"。嵌入模式改用点对点的 `resetSignal`，并且不监听那个全局事件。
- **历史列表必须是浮层**，不能和对话区二选一渲染 —— 条件渲染会把正在跑的那一轮
  卸载掉，而"发出去之后翻一下历史"是再正常不过的动作。
- 验证台补了 `?approval=1`：假流此前从不发 `permission_request`，于是"确认卡长什么样、
  点了之后流怎么继续"这条最要紧的链路一次都没被验过。
