# ADR-0026：运营驾驶舱接日常运营数据（促销倒计时 + 广告看板 + 就地调整）

- 日期：2026-08-23
- 状态：已采纳

## 背景

驾驶舱原本五个标签页（大盘流量 / 关键词 / 竞品监控 / 自有 ASIN / 类目大盘）全部是
**市场侧**数据——看的是别人。运营每天真正要盯的另外半边是**自家的**：报了的活动
什么时候结束、哪个 ASIN 的券快到期、广告花得对不对、要不要马上调。这半边一直
只能去亚马逊后台看。

## 决策

在驾驶舱加两个标签页，数据来自领星 OpenAPI（已接入的通道），并留好第二数据源的位置。

### 一、促销倒计时的数据从哪来

四条活动列表路由 + 一条 ASIN 维度路由，**本机 2026-08-23 实签调用全部 `code=0`**：

| 路由 | 用途 |
|---|---|
| `/basicOpen/promotionalActivities/coupon/list` | 优惠券（起止时间、预算、已花、领取/兑换数） |
| `/basicOpen/promotionalActivities/secKill/list` | 秒杀（Best Deal / Lightning Deal） |
| `/basicOpen/promotionalActivities/manage/list` | 管理促销 |
| `/basicOpen/promotionalActivities/vipDiscount/list` | 会员 / Prime 折扣 |
| `/basicOpen/promotion/listingList` | **按 ASIN** 的促销窗口 |

**ASIN 只能从最后那条拿**：活动列表接口不返回 ASIN，而"哪个 ASIN 的券要结束了"
正是这块面板存在的理由。所以按 `promotion_id` 把两份数据挂在一起。

### 二、两条必须如实告诉用户的现实

1. **领星的促销数据不是 API 直连亚马逊拿的，是浏览器插件抓的。** 官方原话：
   「该模块数据是通过 LINGXING助手 获取的，需要登录 LINGXING助手保持后台在线去获取数据」。
   插件掉线时接口**照样返回 200 和旧数据**，倒计时会安安静静地停在过期的值上 ——
   比没有倒计时更危险。所以每条记录都带 `last_sync_time`，面板顶部常驻新鲜度提示，
   超过 24 小时明确说"插件可能已离线"。
2. **时间是站点当地时间的裸字符串**（`"2026-08-24 23:59:00"`，不带时区）。按服务器
   时区解释，UK 的活动会差 7~8 小时 —— 正好是"以为还有一天、其实已经结束"这种最坏的
   错法。新增 `app/core/marketplaces.py`，以 `marketplace_id` 为键存站点时区
   （本机 11 个店的 id 已逐条核对）。

不依赖插件的替代通道是亚马逊官方 SP-API 报表
（`GET_COUPON_PERFORMANCE_REPORT` / `GET_PROMOTION_PERFORMANCE_REPORT`，均返回
起止时间与预算），需要 SP-API 授权 + 品牌注册。数据层按 provider 抽象留好了位置，
接上即可切换。

### 三、广告看板做后台不做的四件事

后台给的是"ACOS 是多少"，运营要判断的是"这个数好不好、要不要动、动多少"。所以：

1. **目标 ACOS 由毛利率自动推**（平衡 = 毛利率，目标 = factor × 毛利率），
   直接复用 `lingxing_optimizer` 的 `_store_margin` / `_campaign_margins` ——
   同一个数在两个板块里不能有两套算法。
2. **今日预算消耗进度**：今天已花 / 日预算。"下午三点就烧完"是当天必须处理的事，
   后台却要点进每个活动才看得到。
3. **异常自动标注**，每条带一个可直接点的调整意图。
4. **小时曲线**：`/pb/openapi/newad/spCampaignHourData`（实签 `code=0`）。这条路由
   补上了 IvyeaAgent 方案书里标记为"未公开"的那块能力。

### 四、页面读缓存，不直连

**实测：9 个店 × 1 天的广告报表冷启动要 24.7 秒**（领星限流 340ms/次，且一次只能
取一个店一天）。7 天窗口是分钟级。让页面直连去等这个，用户只会得出"这玩意儿比
亚马逊后台还慢"的结论。所以后台按周期预热（`cockpit_sync`，**默认关**），页面永远
读缓存，`force=1` 才现拉。

### 五、就地调整走既有写通道，但给小幅止血开一条快车道

调整复用 `lingxing_operate` 的工单制（护栏 → 复核 → 人工确认 → 回滚快照）。
但完整的三重 LLM 复核要十几秒；一个改 bid 要等十几秒的界面没人会用，运营又回到
后台去改 —— **一个没人用的安全流程，安全性等于零**。

于是给**小幅止血动作**开快车道：跳过 LLM 复核，直接进"等人确认"。三条硬约束写在
`fast_lane_decision` 里，任何调用方都绕不过：

1. **方向必须是止血**：数值只能调小，状态只能转 `paused`。提预算 / 加 bid / enable
   永远走全复核。
2. **幅度 ≤ `lingxing_fast_lane_max_pct`**（默认 15%）。
3. **只在「逐项确认」档生效**。自主执行档下没有人看着，复核就是最后一道闸 ——
   那时候省掉它，等于无人监督地改线上数据。

省掉的只有复核。确定性护栏、人工确认、回滚快照，一道没少。默认关：老用户升级后
行为与升级前完全一致。

### 六、告警不在这里

促销临期、优惠券预算见底、广告异常的**飞书推送在 IvyeaAgent 的巡检里**（它有节流
去重、状态跃迁判定、卡片版式和审批按钮）。ops 只负责"看"和"调"。在两边各放一套
阈值，结果只会是配置打架，或者多一个根本不生效的开关。

## 顺带修掉的一个坑

`lingxing_openapi.classify_route` 用"路径含某个子串就算写"判读写，**两个方向都错**：

- `/basicOpen/promotionalActivities/manage/list`（查管理促销列表）撞上 `/manage/`
  被判成写 —— 整块促销数据在只读通道上取不到；
- `/basicOpen/adReport/spTarget/archiveNegatives`（真的归档否定词）一个子串都没撞上，
  被当成读 —— backstop 这一层形同虚设。

改成按**最后一段的动词全词匹配** + 显式写路由登记表。`addressList` 取到的词头是
"address" 而不是 "add"，天然不会误伤。19 条真实路由 + 边界用例逐条钉进
`tests/test_lingxing_route_classification.py`。

## 代价

- 促销这块的可用性，取决于用户是否让「LINGXING助手」插件保持在线。这是外部依赖，
  我们能做的是**如实显示新鲜度**而不是假装数据永远新。
- 快车道是安全模型上的一次放松。用三条代码级约束 + 默认关 + 一组专门的测试兜住。
- 本机账号没有任何促销数据、广告活动全部归档，所以这两块**只做了契约级 + fixtures
  验收，真数据验收要等一个在投账号**。
