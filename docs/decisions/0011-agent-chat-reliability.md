# ADR-0011 · 会话可靠性：断链不重发，改轮询落盘结果

- **日期**：2026-07-16
- **状态**：已采纳
- **依据**：提交 `fix(agent-chat): 根治"经常撞工具步数上限"与"超时报错但历史里有回答"`

## 背景

工作台里的 agent 对话长期有两个症状：

1. **动不动撞工具步数上限**，逼用户手动打「继续」
2. **前端报超时错误，但历史记录里其实有完整回答**

排查发现是两个独立原因叠加：

- 步数上限：前端硬编码了 18 步，压死了后端 200 步的默认值 —— **真正生效的是最小的那个值**
- 超时：长任务超过 HTTP 超时后前端就报错并重发，而后端其实还在跑，回答最后落了盘

## 决策

1. 步数预算由后端配置决定，前端不再硬编码
2. **客户端断开不打断后端轮次**，服务端加心跳保活
3. 前端超时后不重发，改成**轮询落盘的回答**

## 理由

- 「重发」是最坏的处理：后端已经在跑的轮次不会停，重发等于同一件事跑两遍，还翻倍花钱
- 长任务本来就会超过任何合理的 HTTP 超时，正确的模型是「提交任务 + 查结果」，不是「等响应」
- 步数上限散落在多处硬编码，任何一处小值都会成为实际上限

## 后果

- 配套加了 15s 心跳、带知识引证的回答恢复流式输出（`defer_citation_text` 开关）
- 后续所有长任务板块都按同一套模式做：落盘 + 轮询 + 断开不打断
- 教训：**同一个参数不要在前后端各写一份默认值**
