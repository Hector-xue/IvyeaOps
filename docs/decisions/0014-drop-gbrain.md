# ADR-0014 · 彻底摘掉 GBrain

- **日期**：2026-08-16
- **状态**：已采纳
- **依据**：v1.9.0 / v1.10.0 / v1.10.1 三个版本（PR #111 / #114 / #115 / #116）

## 背景

[ADR-0010](./0010-knowledge-base-front-door.md) 把知识库前门切到了 IvyeaAgent，但一个月后
才发现**代码依赖一直还在**：13 个知识库函数里有 8 个仍要启动外部 gbrain 二进制。

同时 IvyeaAgent 做出了随包自带的语义检索（int8 ONNX 模型，装完即用），GBrain 存在的最后一个
理由 —— 语义检索 —— 也没有了。

## 决策

分三步彻底移除：

1. **v1.9.0 / v1.10.0** —— 知识库的全部能力（概览、统计、体检、搜索、页面、文件、上传、
   对话引用）只靠 IvyeaAgent 工作，GBrain 仅作老机器回退
2. **v1.10.0** —— `gbrain_service.py` 改名 `brain_files.py`，文件层不再有外部程序痕迹
3. **v1.10.1** —— 移除只为 GBrain 存在的「兼容 · Ollama Embedding」安装项

## 理由

- 少约 450MB 依赖（`~/.bun` + GBrain 源码），新用户装机成功率更高
- GBrain 必须 pin 到特定 commit 才能用（新版废弃了 pglite），这个约束本身就是长期负担
- 一个自托管产品，依赖越少越好

## 后果

- IvyeaAgent 离线时知识库会**明确报「未连接」**，而不是悄悄返回空结果 —— 因为没有回退了，
  返回空会让人以为库里根本没内容
- 从 GBrain 导入的历史卡片统一标成 `legacy_gbrain`，需要在按分类过滤时还原它们原本的分类，
  否则内容最多的那批会被整体滤掉
- 教训同 ADR-0010：**摘掉一个依赖要检查所有调用点，不能只换前门**
