# ADR-0027：一轮任务按发生顺序读，直播和刷新后必须是同一个东西

- 日期：2026-08-27
- 状态：已采纳

## 背景

任务台此前把一轮 assistant 拍成两坨：**所有工具堆在上面一块执行过程，所有话拼在
下面一个气泡**。长任务里那块过程有一两百行，用户的原话是"一大堆叠在一起"、
"怎么汇报进度没有即时分段式汇报"。

而同一批反馈里还有一句，它直接指出了正确答案：

> **"好像只有回答完之后刷新一下才能看到分段式汇报的过程。"**

刷新之后是从存档恢复的，而存档里每条 assistant 消息本来就是一段
（`lib/sessionRestore` 按消息切成轮次）。也就是说 —— **正确的形态一直存在，
只是直播时没有。**

agent 干活的形状本来就是「说一段 →（去调几个工具）→ 再说一段」。

## 决策

三件事：

1. **直播时也分段**。事件流层（`lib/turnStream`）在**工具开始跑的那一刻**把已经
   说完的那段话封起来，锚上"当时已有多少步"。`components/console/TurnBody` 按这个
   锚把正文段和步骤切片交错铺开。
2. **事件流的处理只留一份**。直连（`POST /chat/stream`）和接进活轮
   （`GET /chat/sessions/{id}/live`）共用同一套 handler —— 各写一份的话，早晚变成
   "自己发起时看到的过程"和"切回来看到的过程"不一样，而这种不一致最难被发现。
3. **旁白不是结论**。中间那些"边做边说"的段落只留一条引线，不做成卡片；一轮里
   会有四五段，都套上框的话最后那份真正的回答就淹在里面了。

## 理由

- 段的边界**不需要新的服务端协议**：SSE 的到达顺序天然就是发生顺序，第一个 step
  到达就是"上一段说完了"。（接进活轮时这条顺序由 agent 的 `tlen` 保住，
  见 agent 的 ADR-0024。）
- 旁白**不复用 `.cc-answer`**：安静/琉璃两套皮肤对那个类有 `padding:0 !important`
  和 `border-color:transparent !important`（它们的主张是"把盒子全拿掉"）。挂上去
  自己的样式会被整段抹掉 —— 实测 computed 出来是 `0px` / `transparent`。

## 后果

- 一轮读起来是：`过程 → 旁白 → 过程 → 旁白 → 结论`，和刷新之后从存档恢复出来的
  形态一致。
- 思考段的区间必须**左闭右开**（最后一组闭合）。写成闭区间时同一段思考会在相邻
  两组里各画一次 —— 这个错法在验证台上一眼可见，`e2e/live-turn.mjs` 钉住了它。
- 验证台的假流也跟着改成"工具之前先说话"。此前假流里一个字都不在工具之前，
  分段这件事在验证台里根本看不出来，改坏了也验不到。
