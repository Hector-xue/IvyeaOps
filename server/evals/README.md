# 评测案例

一个案例就是一个 json 文件，放在 `cases/<suite>/` 下。**攒案例不需要懂 Python** ——
从真实工单里脱敏出一个，往目录里丢一个文件就行。

```json
{
  "prompt": "要系统做什么",
  "input": { "任意结构的输入数据": "..." },
  "expected_points": ["人工标注的合格要点，一条一句"],
  "guardrails": ["不该做的事，比如：点击数<15 的词不得建议否定"],
  "notes": "数据来源、这个案例想验什么"
}
```

`id` 不写就用文件名。

## 从真实任务生成（推荐）

手工从报表里抠数据、脱敏、排版，一个案例要花不少时间，而每个套件需要 20 个。
用这个把前三步自动化：

```bash
# 先预览，不写任何文件
python -m app.evals.make_case --from-job <广告审计任务id> --my-brand 你的品牌名

# 确认无误再写
python -m app.evals.make_case --from-job <id> --my-brand 你的品牌名 --write
```

它做的脱敏：ASIN 换成稳定化名；金额与量级按同一系数缩放（**比值不变** ——
ACOS、转化率、CPC 都还对得上，绝对花费不再泄露经营规模）；你指名的品牌精确替换。
指定的品牌一处都没命中会**拒绝写文件**（你以为遮住了、实际没遮，是最坏的结果）。

不做的事：**不自动猜哪个是品牌**。没有词典分不出 belro（品牌）和 backyard（普通词），
实测一次会报十几个 battery / camera 这样的常见词，而一个每次都报十几条的警告，
只会训练你条件反射地跳过它。所以只问你唯一知道答案的那件事：你的品牌叫什么。

生成的是**骨架**，`expected_points` 是空的 —— 那一步必须人工。绝不能拿系统自己
上次的输出去填：那等于让模型跟自己的旧答案比，分数再高也只证明它前后一致。
填完之前这个案例跑不起来（加载时会直接报错，不会当成"没有要求所以都算过"）。

## 怎么写出有用的案例

**要点写"必须命中什么"，不要写"应该讲得好"。** `"把 'trail camera 4k' 判为浪费：312 次点击、$486.20、0 单"` 是可判定的；`"分析应该深入"` 不是。

**留几个陷阱案例。** `cases/ads/hallucination_trap.json` 就是：数据故意给得极少，看模型会不会自行脑补竞品。一套只有"正常题"的评测，测不出最该测的东西。

**数据必须脱敏。** 案例会进 git、会随开源仓库发出去。ASIN 换掉、店铺名去掉、金额可以按比例缩放。

## 跑

判官必须与被测模型**不同** —— 同一个模型给自己打分会系统性偏高，它认可的正是
它自己会产出的那种东西。没配判官时评测会报 `skipped` 并说明，不会假装通过。
